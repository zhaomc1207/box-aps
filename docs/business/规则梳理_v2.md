# BOX APS 规则梳理 v2

## 1. 文档范围

本文基于以下资料整理：

- `APS系统数据表目录.xlsx`
- `BOX-智能排产约束规则.xlsx`
- `0403-科大-联宝APS业务交流-逐字稿文本.txt`
- `0403业务规则交流.md`
- 必要时参考 `BOX-APS脱敏数据-2.xlsx`

本文聚焦 `box` 业务，不讨论 `server` 业务。

## 2. 当前样例数据口径

当前脱敏数据中明确未出现以下三张表：

- `aps_schedule_cycle_merge_setting_input`
- `aps_schedule_demand_expand_input`
- `aps_change_model_input`

结合目录表、逐字稿和脱敏数据，当前样例还需要注意两点：

1. 当前样例里存在 `aps_merge_priority_setting`，它对应的是“排前合并阶段顺序配置”，不是订单级优先级权重表。
2. 目录表里还有一张 `aps_schedule_merge_priority_setting_input`，但当前脱敏数据里没有看到对应独立 sheet；结合会议记录，联宝也提到过“有一张 merge 相关表名可能标错”，因此当前样例只能明确确认“排前合并阶段配置”存在，不能确认“合并后 demand 再排序配置”已经单独启用。

## 3. 业务主线

### 3.1 上下游关系

联宝明确说明，APS 不是从原始订单直接开始排产，而是依赖上游系统先完成业务处理，再把可排需求送入 APS。  
上游已经做过的事情包括：

- 订单转 demand
- 物料齐套判断
- fix / prelock / preplan 等业务标识准备
- 部分 lot、fix 顺序的前置处理

所以 APS 输入表里虽然保留了很多完整业务链字段，但不是所有字段都要进入排产。

### 3.2 排产对象

当前排产的基本对象不是原始订单号，而是 `demand_id`。

原因是：

- 一个订单可能拆成多个 demand
- FAI、FIX、lot、open MO、rolling MO 等都会改变真正的排产粒度
- 后续规则表、FIX 表、FAI 表、调整排程表都是围绕 `demand_id` 关联

### 3.3 排产窗口

联宝当前 `box` 业务按 72 小时窗口滚动排产，分三层：

1. `Fix`：未来 24 小时，固定排程
2. `Prelock`：24 到 36 小时，预锁定排程
3. `Preplan`：36 到 72 小时，预计划排程

这样做的目的不是数学建模本身，而是为了让采购、备料、物流等环节提前准备。

### 3.4 当前样例的厂区口径

业务要求算法支持多厂区，但当前脱敏样例实际上基本是单厂区场景：

- `pu_site` 主要为 `LCFC`
- `plant` 主要为 `CN06`

因此当前样例可以按单厂区理解，但模型不应写死成单厂区。

## 4. 核心业务字段

### 4.1 `mcode`

`mcode` 本质上就是业务侧说的 `BU`，是整个排产里非常关键的分类维度。

它的作用包括：

- 区分不同业务口径
- 决定优先级配置按哪套规则解释
- 决定 UPH、换线时间、合并规则等按哪套配置读取
- 在多业务并行场景下决定哪些需求放进同一轮排产

### 4.2 `pn` / Master PN / `model`

`pn` 自身不是排产规则，但它是把 demand 关联到产品属性的桥梁。  
通过 `pn` 去主数据表可以拿到：

- `model`
- `series`
- `program`
- `texture`
- `color`

其中 `model` 是最关键的产品维度之一，因为它直接影响：

- UPH 选取
- 线体匹配
- 换线时间
- 班内机型合并
- 物料项排序

### 4.3 `mr_day`

`mr_day` 是物料齐套日期，也是最典型的“不可早于该日期投产”的门槛字段。  
业务上真正卡控排产的是“齐套相关日期”，而不是状态文字本身。

### 4.4 `mo` 与 `lot`

`mo` 是生产工单。  
`lot` 是把多个小单合并后的批次号。

联宝 `box` 业务小单非常多，按工单逐单生产会导致频繁切换，所以 lot 是现场执行层面非常重要的组织单位。  
业务上希望：

- 相同 `mo` 尽量连续
- 相同 lot 尽量连续
- 不要把同一 lot 打散成 `A-B-A`



### 4.5 交付相关日期

当前排产真正关注的交付相关日期主要有：

- `ots_date`
- `fpsd`
- `ship_day_two`

会议已明确说明：

- 第一类 `ship_date` 更像订单系统粗算日期
- `ship_day_two` 才更接近排产/出货计划真正使用的日期

因此 D+2 出货类规则应优先基于 `ship_day_two` 理解。

### 4.6 订单标识类字段

当前对排产更有意义的订单标识包括：

- `pre_lock`
- `pre_plan`
- `om_urgent`
- `fast_ship`
- `cust_svc`
- `fix_flag`
- `demand_type`

其中：

- `fast_ship` 既会影响优先级，也会影响 UPH 选取
- `cust_svc` 可理解为定制化订单标识
- `demand_type` 当前样例里常见 `MR`、`LOT`、`ROLLING_MO`、`OPEN_MO`

## 5. 规则梳理

### 5.1 需求释放规则

#### 5.1.1 MR Date 约束

需求排产日期不能早于 `mr_day`。  
这是标准硬约束。

#### 5.1.2 工单与订单的区分

业务规则表里区分了两类对象：

- 已开立待生产工单
- 待生产出货订单

从业务上看，已经开立并进入执行节奏的工单，不应该被重新打散重排；而待生产订单才是主要待决策对象。

#### 5.1.3 当前样例中的 `demand_type`

当前样例里主要有四类：

- `MR`
- `LOT`
- `ROLLING_MO`
- `OPEN_MO`

其中：

- `ROLLING_MO`、`OPEN_MO` 在优先级表里有专门优先级
- `LOT` 说明该需求已经进入批次化组织

### 5.2 Fix / Prelock / Preplan 规则

#### 5.2.1 Fix

Fix 是当前排程窗口内最强的锁定层。

目录表中 `aps_schedule_demand_fix_input` 定义了：

- `fix_day`
- `fix_shift`
- `fix_line`
- `fix_sequence`
- `fix_qty`
- `fix_type`

但当前脱敏数据实际表头是：

- `fix_day`
- `fix_shift`
- `fix_line_id`
- `fix_seq`
- `fix_qty`

当前样例观察到：

- `aps_schedule_demand_fix_input` 一条 `demand_id` 只对应一条 fix 记录
- `fix_qty` 与 `demand_base.qty` 全部相等

这意味着在当前样例里，Fix 不是“部分锁定”，而是“整单精确锁定到某天某班某线，并给出班内顺序”。

#### 5.2.2 Prelock / Preplan

`pre_lock` 和 `pre_plan` 不是单独的固定排产表，而是 demand 属性。  
它们主要通过优先级表进入排产。

当前样例里：

- `pre_lock = X` 有较多记录
- `pre_plan` 基本全为 `0`

因此当前样例里真正活跃的是 `pre_lock` 逻辑，而不是 `pre_plan` 逻辑。

### 5.3 优先级规则

#### 5.3.1 优先级配置方式

优先级规则来自 `aps_schedule_priority_setting_input`，当前脱敏数据 sheet 为 `aps_schedule_priority`。

表的核心逻辑不是“每个订单一条优先级”，而是“按规则配置优先级”：

- `priority`：优先级层级
- `priority_group`：配置组
- `condition_key`
- `condition_type`
- `condition_value`
- `kpi`

#### 5.3.2 组内与组间逻辑

会议已明确说明：

- 同一 `priority_group` 内是“且”关系
- 同一 `priority` 下不同 `priority_group` 之间是“或”关系

所以真正的命中逻辑应该是：

1. 先判断一个组内的所有条件是否同时满足
2. 只要某个组命中，就属于该优先级
3. 如果命中多个优先级，按最靠前优先级解释

#### 5.3.3 日期类条件的解释方式

如果条件字段是日期字段，例如：

- `ots_date`
- `fpsd`
- `ship_day_two`

则条件值不是直接和日期字符串比较，而是按“字段日期相对当前排产日的差值”解释。  
例如 `D+2`、`D+3->D+7` 都属于这种配置。

当前样例中也能看到这类范围配置，例如同一组内用两条条件行描述一个时间窗口。

#### 5.3.4 当前样例中的实际优先级主题

当前样例里真正出现的优先级主题包括：

- `Rolling MO`
- `Open MO`
- `Pre-Lock`
- `OTS=D+1 / D+2 / D+3->D+7`
- `FPSD=D+1 / D+2 / D+3->D+7`
- `ShipDate=D+1 / D+2 / D+3->D+7`
- `GLOBALS`
- `Others`

这说明当前业务不是把优先级写死在程序里，而是通过规则表按业务需要组合。

#### 5.3.5 `kpi` 的当前口径

目录表里 `kpi` 定义为全局目标方向：

- `qtymax`
- `ordermax`

字段位置是在优先级规则行上，不是单独一张全局参数表。

当前样例实际观察到：

- 非空 `kpi` 只有 `qtymax`
- 没看到 `ordermax`
- 也有不少空值

因此当前样例可以按“版本级目标偏向 `qtymax`”理解，但正式模型不能把 `kpi` 误写成天然全局唯一值。

#### 5.3.6 KPI 评价范围

业务规则表明确指出：

- OTS、FPSD 是重要优化目标
- 对受 MR 限制的订单，OTS/FPSD 评价应做例外处理

因此“能不能排”和“是否计入交付 KPI”不是完全同一件事：

- `mr_day` 仍然是硬门槛
- 交付 KPI 评价范围还要再按业务规则做筛选

### 5.4 产能与线体规则

#### 5.4.1 线体与日历

线体基础信息来自 `aps_schedule_line_input`。  
当前样例观察到：

- 共 17 条线
- `normal` 线 16 条
- `cell` 线 1 条

日历来自 `aps_schedule_line_calendar`，主要给出：

- 哪天哪班开班
- 班次起止时间
- 是否 `ON/OFF`

休息等不可生产时段来自 `aps_schedule_off_time_input`。

因此产能的正确理解应是：

1. 先用日历确定班次时段
2. 再扣减休息/停机时间
3. 再减去已继承任务占用
4. 剩余时间才能给当前待排需求

当前样例里没有看到独立的 `aps_schedule_reserver_input` 数据，因此“产能预留”这项能力在规则层存在，但在当前样例里更适合按“若无数据则预留时长为 0”理解。

#### 5.4.2 UPH 规则

UPH 来自 `aps_schedule_uph_input`。  
它不是简单按 `model` 一维维护，而是至少同时受以下维度影响：

- `line_id`
- `day`
- `shift_seq`
- `model`
- `mcode`
- `fast_ship_flag`
- `cust_svc`

当前样例里同一条 `line_id + day + shift_seq + model` 往往存在多条记录，差异来自：

- `fast_ship_flag`
- `cust_svc`
- `priority`
- `transform_priority`

因此 UPH 的业务口径不是“查到就用”，而是“按需求属性匹配，再按配置优先级选最合适的一条”。

#### 5.4.3 线机匹配

当前样例没有看到单独的“线机匹配表”。  
从业务和数据上更合理的理解是：

- 某个 demand 能否在某线某班生产，首先看是否能匹配到合法 UPH
- 匹配不到 UPH，就视为该 demand 在该线班不可生产

### 5.5 Cell 线与大小单规则

#### 5.5.1 业务含义

业务规则表指出：

- 客制化小单
- `fast_ship` 订单

优先走 `cell` 线。

这更像“业务偏好 + 柔性资源优先使用”，不一定都是硬约束。

#### 5.5.2 当前样例里的大小单配置

当前样例只有一条 `aps_schedule_order_qty` 配置：

- 一条线
- `model = *`
- `flag_type = 2`
- `small_qty = 10`

按目录表解释：

- `flag_type = 1`：只排小单
- `flag_type = 2`：大小单都可排
- `flag_type = 3`：只排大单

因此当前样例里只能确认：

- 有一条线配置了“小单阈值 = 10”
- 且该线并不是“只排小单”或“只排大单”，而是两类都能排

所以当前样例不足以把“cell 线只能排某类订单”建成硬约束，更适合建成偏好目标。

### 5.6 限制排产规则

限制规则来自 `aps_schedule_limit_setting_input`，当前脱敏数据 sheet 为 `aps_schedule_limit_setting`。

业务侧解释非常明确：

- 前台维护的一条限制规则，落到表里可能拆成多行
- `group_id` 表示一条完整限制实例
- `type` 表示当前这一行在该限制实例里扮演什么角色

目录表中 `type` 的口径是：

- `1`：PO 条件字段类型
- `2`：限制条件字段类型
- `3`：限制值字段类型

也就是说，这张表不能逐行孤立解释，必须按 `group_id` 聚合后再解释成完整规则。

当前样例里实际只看到：

- `mcode = CB`
- `limite_type = Qty or Line`
- `scene_type = 0`

对应示例是某机型在某班次、某限制线的限制场景。  
这说明“限制机制存在”，但当前样例里并没有覆盖所有业务类型。

### 5.7 FAI / 首件规则

FAI 规则来自 `aps_schedule_demand_fai_input`。

目录表定义：

- `group_id`：一组 FAI 关联需求
- `group_first`：优先首件
- `lead_time`：间隔时间
- `type`：`FOT/FAI/RPQ`

业务规则表给出的例子是：

- FAI 首片 2 pcs
- 与其余数量间隔 8 小时
- 首片 pass 后再投入余量

当前样例实际观察到：

- 全部是 `FAI`
- `group_first = 1` 的 demand，在基础需求表里数量全部是 `2`
- `group_first = 0` 的是余量需求
- `lead_time` 字段当前样例全为 `1`

因此应按以下口径理解：

1. “2 pcs 首片”在当前样例里是成立的
2. 具体等待时长不能写死成 8 小时，应该以 `lead_time` 字段为准
3. 业务规则表中的“8 小时”更像典型业务例子，不应覆盖掉配置字段

### 5.8 继承排程规则

`aps_adjust_schedule_input` 不是普通待排需求表，而是“上一轮排程/人工调整结果输入表”。

目录表给出字段：

- `schedule_qty`
- `line_id`
- `schedule_seq`
- `schedule_day`
- `shift_seq`

当前样例实际观察到：

- 共 2013 条记录
- 其中 1725 条 `demand_id` 同时存在于当前 `demand_base`
- 另外 288 条 `demand_id` 不存在于当前 `demand_base`
- 对于存在于 `demand_base` 的记录，`schedule_qty` 与 `base.qty` 全部相等
- 一条 `demand_id` 只对应一条调整记录

这说明这张表在当前样例里至少承载了两类作用：

1. 对当前仍在待排集合里的需求，给出“已经约定好的排产结果”
2. 对当前不在待排集合里的任务，表示“已有排程占位”，会占用未来线体产能

因此它不能简单理解成“当前 demand 的软锁定表”，更合理的业务理解是：

- 一部分记录是当前模型的精确继承锁定
- 另一部分记录是外部已排任务，对当前模型表现为产能占用

### 5.9 合并、lot、材料项排序与换线

#### 5.9.1 lot 连续性

会议明确提到：

- lot 是现场执行的重要组织单位
- 同一 lot 应尽量连排
- 不希望出现 `A-B-A`

对 FIX 任务，业务侧已经尽量在前端把同 lot 顺序准备好，但算法侧仍建议做校验或细排保护。

#### 5.9.2 排前合并阶段配置

当前样例存在 `aps_merge_priority_setting`，目录对应 `aps_merge_priority_setting_input`。

它的字段只有：

- `priority`
- `priority_desc`
- `code`

当前样例三类 `mcode` 都出现了相同的四级阶段：

1. `pn属性合并`
2. `Demand属性合并`
3. `颜色材料项合并`
4. `pn合并`

因此这张表表达的是“排前合并步骤的先后顺序”，不是“订单排产优先级权重”。

#### 5.9.3 材料项排序规则

`aps_schedule_order_ruler_input` 对应当前样例 sheet `aps_schedule_order_ruler`。

目录表说明它是颜色/材料项排序规则。  
当前样例里实际非常清晰：

- 只看到 `TN`
- 按线体配置
- `model = *`
- 每条线都有 4 层排序键

当前样例的 4 层排序键顺序是：

1. `kb`
2. `log_up_assy`
3. `cover_assy`
4. `pcba`

所以它更像“班内同线任务如何排序”的细排规则，而不是主模型可行性约束。

#### 5.9.4 换线时间规则

换线时间来自 `aps_change_time_input`。  
目录字段包括：

- `mcode`
- `model_one`
- `model_two`
- `program_one`
- `program_two`
- `material_type_one`
- `material_type_two`
- `pu`
- `change_time`

业务交流中明确给出的匹配顺序是：

1. 先按 `mcode + pu`
2. 再找 `model_one -> model_two` 正向精确匹配
3. 找不到再找 `model_two -> model_one` 反向精确匹配
4. 再退到 `program_one -> program_two`
5. 再看反向 `program_two -> program_one`
6. 再退到带 `*` 的泛化规则

当前样例里实际只看到最泛化的默认行：

- `TN` 默认 `3` 分钟
- `LD` 默认 `3` 分钟
- `DT` 默认 `3` 分钟

所以当前样例能确认“换线时间机制存在”，但没有看到更细的机型对机型配置。

#### 5.9.5 机型相似度表

`aps_change_model_input` 在目录表中存在，但当前脱敏数据不存在。  
因此当前样例无法支持“按相似度修正换线时间”的逻辑。

## 6. 当前样例下更适合怎么建模

### 6.1 适合放进主模型的

- MR Date 不可提前
- 线体班次产能
- 日历与停机时间
- 基于 UPH 的线机匹配
- FIX 精确锁定
- 当前 demand 的继承排程精确锁定
- 外部已排任务的产能占用
- FAI 首件与余量的先后关系
- 交付 KPI 未达成量
- 主优先级驱动的目标函数

### 6.2 更适合放进二阶段细排或启发式的

- `fix_seq`
- `schedule_seq`
- lot 连续
- 班内材料项排序
- 精确换线顺序
- `A-B-A` 消除
- 同 lot 尽量连续

### 6.3 当前样例下不应强行建成主模型硬约束的

- `cell` 线只排某类订单
- 定制化/快单必须上 `cell` 线
- 颜色材料项合并后的 demand 排序
- 机型相似度修正换线时间

原因不是这些业务不重要，而是当前样例数据没有把这些规则完整落到可直接求解的配置表上。

## 7. 对后续数学模型的直接影响

结合本次业务对齐，后续数学模型至少应修正以下口径：

1. `aps_schedule_priority` 必须按 `priority_group` 做“组内且、组间或”解释，不能逐行独立命中。
2. `aps_merge_priority_setting` 应解释为“排前合并步骤顺序”，不能直接写成订单级权重。
3. 当前样例里的 `FIX` 应按整单精确锁定处理，而不是按“部分锁定”默认处理。
4. `aps_adjust_schedule_input` 不能只写成“当前 demand 的锁定”，还要识别其中一部分是外部已排任务占用产能。
5. `ship_day_two` 才是更适合进入 D+2 出货相关规则的日期字段。
6. FAI 等待时长应使用表里的 `lead_time`，不能把“8 小时”写死在模型里。
7. 换线时间应按“正向 model、反向 model、正向 program、反向 program、通配默认”顺序匹配。
