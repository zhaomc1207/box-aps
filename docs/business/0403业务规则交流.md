这份《0403-科大-联宝APS业务交流-逐字稿文本》的核心，是一次“数据字段澄清会”。科大团队已经拿到联宝提供的脱敏数据、输入输出表清单、约束/KPI说明，但因为不熟业务，很多字段只能“靠猜”，所以这次会议的目标不是讨论算法方案本身，而是把联宝 box 业务里的排产流程、关键字段、配置表含义、哪些字段要用/哪些可以忽略，系统性对齐清楚。

**一、会议背景与目标**  
联宝上周提供了三类资料：

1. APS排产输入/输出表清单，区分 box 和 server 两类业务。
2. 脱敏后的真实运行数据，取自 3月10日 某次真实 run 的输入数据。
3. 排产过程中的约束条件，以及算法需要优化的 KPI 目标说明。

科大团队的困惑主要有三类：

1. 不理解排产业务流程本身。
2. 不清楚主需求表和相关表中字段的业务含义。
3. 不确定哪些字段/表需要在算法中真正考虑，哪些只是联宝上游/下游系统顺带带出来的冗余信息。

联宝这边的总体回答是：

1. 先按业务去理解数据，而不是先盯着表结构。
2. 提供的数据里有很多字段来自完整业务链路，不是排产都要用。
3. 可以逐字段、逐张表过一遍，把真正影响排产的维度和规则拎出来。

**二、联宝 box APS 排产业务的总体逻辑**  
联宝说明，APS排产强依赖前端 RPS / AMA 类系统。上游先完成订单齐套判断，再把结果交给 APS 排产。因此传给科大的主表实际上是一张“完整业务表”，其中既包含排产信息，也包含出货、采购备料等其他环节的信息，所以并不是所有字段都需要纳入排产。

当前 box 业务的排产窗口是 72小时，分成三层：

1. Fix：未来 24小时 内，固定排程。
2. Prelock：24-36小时，预锁定排程。
3. Preplan：36-72小时，预计划排程。

这样分层的目的，是让采购、物流、备料等环节能提前准备。业务会在 RPS 里给订单打 fix / prelock / preplan 类标记，APS 需要按这些标记及优先级配置来排。

当前实际数据里只有一个厂区，但算法设计上要支持多厂区。每个 demand 会被预先处理好所属厂区，排程时 demand 只能匹配到厂区一致的线体。

**三、对“主需求 / basic input”相关关键字段的澄清**  
这是会议最主要的部分。结论如下。

1. M code  
   它本质上就是 BU。是排产里非常关键的维度。  
   作用：

2. 定义排程版本里包含哪些 BU。

3. 优先级配置通常按 BU 维度区分。

4. UPH、约束、很多配置表都带 M code/BU 维度。  
   补充：

5. 后面有些类似字段是别的业务遗留，可忽略。

6. product code 只是 BU 的业务编码映射，比如 LNB/TNB 对应某些内部 code，本质作用不如 M code 直接。

7. Demand ID  
   它是排产对象 demand 的唯一标识。因为一个订单在特殊情况下可能拆成多个节奏/对象，所以最终排产是以 Demand ID 为主，而不是订单号本身。某些订单相关字段在转成 demand id 后就不再重要。

8. PN / Master PN  
   PN 是成品料号。它本身不是排产核心，但它用于去 Master PN 表里关联出 demand 的物料属性，例如：

9. model

10. service tag

11. 其他后续匹配会用到的属性  
    也就是说，很多排产维度不是直接在 basic input 里原生给出，而是通过 版本号 + PN 关联出来的。

12. Model  
    Model 就是机型，是整个排产里非常重要的维度。  
    作用包括：

13. UPH 维护按 model 维度。

14. 某些特殊 flag 的 UPH 是 model + flag 联合决定。

15. 合并排序常按 model 组织。

16. 换线/换型统计按 model 计算。  
    联宝强调，换线优化就是算法的重要价值之一。因为联宝有几百个 model，而线体有限，同一条线一定会排多个 model，model 间切换会损失产能、需要换治具/换人等，因此算法要尽量减少换型。

17. 齐套日期 / money / CPN / status  
    会议里虽然转写有口误，但核心意思是：

18. 真正卡控排产的是“齐套相关日期”，也就是物料可允许最早投产时间。

19. 状态类字段本身不重要，排产主要看具体日期值。

20. 某些状态例如是否“当天齐套”或“非无限期齐套”，最后仍要落到日期判断上。

21. MO  
    MO 是生产工单。业务逻辑是“先有订单，再转成生产工单”。  
    排产中的作用：

22. 相同 MO 往往要连续排。

23. MO 是否为空，会影响 demand 类型识别。

24. 某些 rolling MO、open MO、M码 等类型识别与 MO 字段有关。

25. Lot  
    Lot 是批次号。  
    联宝 box 业务的特点是小单非常多，85%以上是5台以下小单。如果按工单单独备料、生产，会频繁切换，效率很低，所以业务会按规则把多个 MO 合并成一个 lot。之后：

26. 仓库备料按 lot 走。

27. 生产也按 lot 走。

28. 排产里相同 lot 需要尽量连续，不能拆开，避免出现 ABA 式打散。

**四、哪些字段/表重要，哪些可以先忽略**  
会议里反复强调：很多字段来自完整业务链，但当前排产不用。

可先忽略或非当前 box 排产重点的，大致包括：

1. 某些其他业务字段，如 shipment type + brand、FOTRPQ 等。
2. 一些系统推算字段，如 FG Ready，它是成品预计 ready/入库时间，和排产本身关系不大。
3. EOP、部分材料类型字段，当前 box 业务不用。
4. 接单日期 等字段，当前排产不重点考虑。
5. 有些表如果脱敏数据里根本没出现，就说明当前没配置，可先不考虑。

联宝也特别说明：

1. 他们给的是完整表，不代表所有字段都要做算法输入。
2. 对科大来说，应该先聚焦实际 run 中存在且当前配置已启用的字段和表。

**五、与订单优先级相关的日期与标识**  
这部分是业务 KPI 和优先级配置的重点。

1. FPSD / First PSD 一类字段  
   它代表第一次承诺给客户的出货日期，是联宝重要的“交付准时性”考核 KPI。排产时会重点关注离当前排产日较近的 FPSD 订单。

2. OTS / OOTS / Order to Ship Day  
   这是客户考核“交付快慢”的重要指标，也是很重要的 KPI，可以进入优先级配置。

3. RSD 一类客户要求出货日期  
   联宝明确说，这类字段当前排查/排产过程里不是重点考虑项。

4. 两个 Ship Date  
   会议解释了为什么有两个 ship date：

5. 一个是订单管理系统按产能/材料交付粗算出来的日期。

6. 另一个 Ship Date Two 是结合实际排产、倒料后调整出的“实际出货日期”。  
   真正排产/出货计划用的是第二个。

7. OM urgent / 提单类 flag  
   它是订单标识。对排产来说，可以理解为提单、急单类属性，能进入优先级配置。

8. Fast Ship  
   它也是订单 flag，作用有两块：

9. 影响 UPH 匹配。

10. 可作为优先级配置条件，标记了 fast ship 的订单可优先排。

11. 一些定制化订单 flag  
    作用与 fast ship 类似：

12. 可以单独配置优先级。

13. 对应单独的 UPH 维护逻辑。

**六、优先级配置表的设计逻辑**  
这部分是会议后半段的关键结论之一。

优先级配置表按 版本号 + M code 维护。主要字段逻辑如下：

1. Priority  
   就是优先级层级。

2. Priority Group  
   组内是“且”关系；组间是“或”关系。  
   也就是：

3. 一个组内多条条件都满足，才命中该组。

4. 同一优先级下，只要命中任意一个组，就属于这个优先级。

5. Condition Key  
   对应 base input 表中的字段名。业务可以非常灵活地配置，比如：

6. FPSD

7. fast ship flag

8. country

9. 各种订单属性字段

10. Condition Type  
    表示比较方式，比如：

11. 等于

12. 大于

13. 其他比较关系

14. Condition Value  
    表示配置值。  
    例如：

15. fast_ship_flag = X  
    表示命中某一优先级。

16. 如果字段是日期，则值需要按“相对当前排产日”解释，比如“大于2”表示“字段日期 - 当前排产日 > 2”。

联宝强调，这张表是业务配置化的核心，很多字段本身不一定写死在算法逻辑里，而是通过这张表控制“哪类订单先排”。

**七、限制表（Limit）怎么理解**  
限制表本质上也是一种配置展开表。

前台业务可能只维护“一条限制规则”，但这条规则可能涉及多个字段，所以落到数据表里会拆成多行：

1. 用 group id 把同一条限制规则聚起来。
2. limit type 表示限制的大类，比如颜色、country、某种线体限制等。
3. type 更像前台配置的子分类或字段分类，本身对算法不是最关键。
4. 一条前台规则可能拆成多条 condition key / condition value 记录。

此外，限制还会区分：

1. 用于 normal 线还是 cell 线
2. 用于哪些线体/线体类型
3. 某些限制与班次、机型、国家等维度有关

也就是说，算法侧更应该把它理解为“按 group 聚合的一组限制条件”，而不是逐行孤立看。

**八、合并/排序/换线相关配置**  
这是排产“排序”和“减少切换损耗”的另一大重点。

1. Schedule Merge / 合并规则  
   存在颜色材料项合并等需求。业务会按一组字段做多级排序/合并。  
   例如：
2. 第一优先按某字段合并
3. 第二优先按某字段合并
4. 后续继续按配置的字段分层合并

联宝建议，未来如果配置项继续增加，最好按类似 JSON 或配置化解析方式处理，不要把字段写死，因为以后可能新增属性而不新增字段结构。

2. 颜色材料项合并  
   只针对开了 MO 的场景。目的是把相同属性的订单尽量放在一起，减少关键切换，方便生产。

3. Priority 在 merge 表里的含义  
   这里的 priority 和前面的“订单优先级 priority”不是一回事。  
   这里表示“第几层合并/排序优先级”，比如：

4. 第一级按 KB

5. 第二级按 Cover  
   之类的字段合并

6. Change Time  
   它是换线时间配置。  
   匹配逻辑大致是：

7. 先找 model one -> model two 的正向精确匹配

8. 找不到再找反向 model two -> model one

9. 再退化到 program one -> program two

10. 最后再退到更泛化的匹配，如 model *  
    其目的就是给算法提供不同 model/program 切换时的换线成本，便于优化换型。

**九、一些特定业务表的含义**

1. Order Qty / 大小单相关表  
   主要定义某些特定线体可排哪些类型订单，例如：

2. 某条线默认主要排 fast ship

3. 产能有余量时可排 normal 订单

4. 可限制只排小单，或大小单都能排

5. 并定义多少数量算“小单”  
   会议里说这类配置是针对特定几条线，不是全线通用。

6. 某些 merge/priority 表  
   有一张表实际是“表名写错/标注错”，另一张才是真正有配置的数据表。也就是说，科大后续梳理时要注意：有些问题不一定是业务逻辑没配，也可能是表说明文档标错了。

**十、最终对齐出来的几个重要结论**

1. 当前讨论聚焦的是 box 业务，不是 server。
2. 排产的核心输入对象是 demand id，不是原始订单号。
3. 核心维度包括：  
   M code(BU)、Demand ID、PN/Master PN、Model、MO、Lot、齐套相关日期、厂区、线体、flag、UPH。
4. 关键配置类表包括：  
   优先级配置表、限制表、合并排序表、换线时间表、大小单/特定线体配置表。
5. 很多字段虽然出现在主表里，但只是完整业务链上的附带信息，当前排产不必全部使用。
6. 优先级不是写死的，很多业务规则应通过配置表解释，而不是硬编码字段优先顺序。
7. 算法需要重点兼顾三类目标：  
   交付准时、交付速度、减少换线/换型损耗。
8. 当前真实数据里有些表没出现，意味着当前没配置，可以先不纳入实现。
9. 当前数据层面的主要疑问在会上基本对齐；后续科大团队会继续梳理，如果再发现问题，再和联宝沟通。
